# SWIM D-work 設計書

要件は `docs/requirements.md`。この文書は、要件定義後の確認で決めた事項と、データベース・権限・通知・実装フェーズの設計をまとめたもの。要件書と食い違う場合はこの文書を優先する。

## 1. 要件確認で決まった事項

| No | 論点 | 決定 |
| --- | --- | --- |
| Q1 | 記録開始後のメニュー変更 | 選手が記録を始めたら、コーチはそのメニューを変更・削除できない（ロック） |
| Q2 | 選手への通知タイミング | 自動では送らない。コーチが「保存して選手に通知」などのボタンを押したときに送る（下記 4章） |
| Q3 | 「実施済み」の印 | 選手が実施画面で「完了」を押したとき。チェックが1つ以上あって完了前なら「実施中」。未チェックが残っていても完了でき、未チェック分はコーチ画面で強調 |
| Q4 | コーチ通知の重複 | 1回の操作で送るコーチ通知は最大1通（下記 4章の条件表） |
| Q5 | 「変更あり」表示 | メニュー設定後の変更だけが対象。表示は「最初の値 → 最新の値」（変わった項目だけ）。コーチが「確認済み」を押すと消える |
| Q6 | 種目の単位 | 「回」と「秒」の2択。5分は300秒として入力・保存する（表示は下記 6章） |
| Q7 | 単独ブロックのセット数 | 実績で修正できる。ブロック単位で実施セット数を1つ持つ（サーキットの実施周回数と同じ扱い） |
| Q8 | 種目削除時の確認 | Q1 により記録がある種目は削除できないため、記録後の確認ダイアログは不要。記録開始前は通常どおり削除できる |
| Q9 | 一括貼り付け先にメニューがある場合 | 一覧で「設定済み」と表示し、上書きするかを選ぶ（初期は未選択）。記録が始まった枠は選べない |
| Q10 | 中止の取り消し | 「通常」に戻せる。中止理由は履歴として残す |
| Q11 | 実績の修正期限 | 期限なし（自分の分のみ） |
| Q12 | 選手の通知設定 | 選手カレンダーのメニューに「通知を有効にする」を置く（独立した画面は作らない） |
| Q13 | 停止した選手 | 停止を解除できる。コーチカレンダーでは初期状態で非表示、絞り込みで表示 |
| Q14 | 技術選定 | 費用ゼロで運用できる構成にする（下記 2章） |
| Q15 | iPhone の対応バージョン | iOS 16.4 以上。それ未満の端末には案内文を表示 |

### Q1 の「記録開始」の定義

選手の操作で次のどれかが記録された時点を「記録開始」とする。

- 種目のチェックが1つ以上ある
- 実績値（回数・秒数・負荷・セット数・周回数）を計画値から1つ以上変更した
- 種目を追加した
- 「完了」を押した

画面を開いただけ、チェックを付けてすぐ外しただけ（すべて計画どおりで、チェックも追加もない状態）はロックしない。ロックはデータベースのトリガーで強制する。

## 3. テーブル設計

日付と時刻は日本時間の `date` 型と `time` 型で保存する（タイムゾーン変換をしない）。「今日」「明日」「22:00以降」の判定は、データベースでは `now() at time zone 'Asia/Tokyo'` を基準にする。

| テーブル | 主な列 | 書き込める人 |
| --- | --- | --- |
| `profiles` | `id`（= auth.users.id）、`role`（coach / athlete）、`display_name`、`color`、`is_active` | コーチ（招待・停止は Edge Function 経由） |
| `events`（予定枠） | `id`、`athlete_id`、`kind`（dryland / swim / meet）、`date`、`start_time`、`place`、`duration_min`、`status`（normal / canceled）、`cancel_reason`、`changed_from`（jsonb：メニュー設定後の最初の日付・時刻・場所・時間）、`change_ack_at`、`created_at`、`updated_at` | 選手本人 |
| `event_cancel_history` | `event_id`、`reason`、`canceled_at`、`restored_at` | トリガーが自動で記録 |
| `menus`（計画） | `event_id`（主キー、1枠に1つ）、`blocks`（jsonb）、`updated_at`、`notified_at` | コーチ |
| `records`（実績） | `event_id`（主キー）、`exercise_results`（jsonb：種目IDごとの checked・実績値・負荷）、`block_results`（jsonb：ブロックIDごとの実施セット数・実施周回数）、`added_exercises`（jsonb）、`completed_at`（完了）、`started`（bool、トリガーが計算） | 選手本人 |
| `templates` | `id`、`title`、`blocks`（jsonb、menus と同じ形式）、`reference_note_id` | コーチ |
| `reference_notes`（参考メニュー帳） | `id`、`title`、`url`、`memo`、`tags text[]` | コーチ |
| `exercise_names`（種目名の候補） | `name`（一意）、`last_used_at` | menus・templates 保存時のトリガー |
| `push_subscriptions` | `user_id`、`endpoint`（一意）、`p256dh`、`auth`、`user_agent` | 本人 |
| `notifications`（送信待ち・送信記録） | `recipient_id`、`kind`、`payload`、`sent_at`、`delivered`、`error` | トリガーが追加、Edge Function が送信（利用者は触れない） |

### メニュー JSON の形式（menus.blocks / templates.blocks）

```jsonc
[
  { "id": "uuid", "type": "single", "sets": 3, "rest_sec": 60, "memo": "",
    "exercise": { "id": "uuid", "name": "懸垂", "value": 8, "unit": "reps", "load": "自重", "memo": "" } },
  { "id": "uuid", "type": "circuit", "rounds": 3, "rest_between_exercises_sec": 15, "rest_between_rounds_sec": 90, "memo": "",
    "exercises": [ { "id": "uuid", "name": "スクワット", "value": 15, "unit": "reps", "load": "自重", "memo": "" } ] }
]
```

- `unit` は `reps`（回）か `sec`（秒）のどちらか
- ブロックと種目には UUID を付け、実績はその UUID と紐づける
- 形式は zod のスキーマを正とし、データベース側にも同じ内容の CHECK 制約（検証関数）を置く

### 設計判断

- 計画（menus）と実績（records）は書く人が違うので、別テーブルにする。権限をテーブル単位で分けられ、計画値の上書きも構造上起こらない
- メニュー本体は jsonb で持つ。並び替えや入れ子を1回の更新で保存できる

## 4. 通知

### 仕組み（フェーズ6で実装）

- 端末ごとの購読は `push_subscriptions`（本人の分だけ読める。登録は関数 `register_push_subscription` 経由で、同じ端末を別の人が使うと購読が移る）
- **コーチ宛て**：`events` のトリガー `events_queue_coach_notification` が条件を判定し、送信待ち `notifications` に1行入れる。選手のアプリが予定を保存した直後に Edge Function `flush-notifications` を呼び、宛先ごとに1通にまとめて送る。取りこぼしは毎晩22時の `nightly-check` が送る
  - DB から Edge Function を直接呼ばない（pg_net・Vault を使わない）ので、DB に秘密の鍵を置かなくてよい
  - 送る内容は DB が決めるため、`flush-notifications` はログイン中の有効な利用者なら誰が呼んでもよい
  - 二重送信を防ぐため、送る前に `sent_at` を入れた行だけを送る
- **選手宛て**：コーチの「保存して選手に通知」などで Edge Function `notify-menu` を呼ぶ。呼び出した人がコーチかを確認し、選手ごとに1通にまとめ、`menus.notified_at` を更新する
- 購読が切れた端末（送信先が 404/410 を返す）は自動で削除する
- 通知の文面は `supabase/functions/_shared/messages.ts`（テストあり）

### コーチ宛て（自動、即時）

対象はドライランド枠だけ。選手本人の操作だけが対象（管理者の操作では送らない）。1回の操作で送るのは最大1通。

| 対象の枠 | 操作 | 通知 |
| --- | --- | --- |
| メニュー未設定 | 「締切後」の日付に追加・移動（締切後 = 前日22:00以降の翌日分、または当日分）。中止の取り消しや種類の変更でドライランドになった場合も「追加」とみなす | 送る（「Aさん 明日 07:00 自宅 30分 が追加されました（メニュー未設定）」） |
| メニュー未設定 | 締切前の追加・変更・中止・削除、場所や時間だけの変更 | 送らない（22時のチェックで拾う） |
| メニュー設定済み | 日時・場所・時間の変更、中止、中止の取り消し（日時を問わない） | 送る（「変更されました（11/10 16:00 → 11/12 16:00）」「中止されました（理由：発熱）」） |

締切の判定は DB の `is_after_deadline(date)`（日本時間）。

### コーチ宛て（毎晩22:00）

Cloudflare Workers の Cron Trigger（`0 13 * * *`、UTC 13:00 = JST 22:00）が Edge Function `nightly-check` を呼ぶ。呼び出しは共有シークレット（`CRON_SECRET`）で認証する。この毎日の呼び出しが Supabase の一時停止対策も兼ねるため、未設定がない日も必ず呼ぶ。
1. 送信待ちの残りを送る
2. 翌日の、中止されていないドライランド枠（有効な選手のみ）のうちメニューがないものを1通にまとめて送る（「明日メニュー未設定：Aさん 16:00 学校 40分／Bさん 18:30 自宅 30分」）。該当がなければ送らない

### 選手宛て（コーチのボタン操作）

- メニュー編集画面のボタンは「保存」と「保存して選手に通知」の2つ。保存したメニューは通知の有無にかかわらず、すぐ選手に表示される
- 保存済みで未通知なら「保存済み・選手に通知する」ボタンが出る
- 一括貼り付けの画面には「選手に通知する」チェック（初期値オン）を置く。編集中の枠と貼り付け先をまとめて、選手ごとに1通にする
- メニューの内容を変えた日時（`menus.updated_at`）が `notified_at` より新しい（または `notified_at` が空）メニューには、コーチのカレンダーで「未通知」の印を付ける。通知日時だけの更新では `updated_at` は変わらない
- 文面
  - 初めての通知：「11/10（火）のドライランドにメニューが入りました」
  - 2回目以降：「11/10（火）のメニューが変更されました」
  - 複数日の場合：「11/10（火）ほか2日のメニューが入りました」（すべて2回目以降なら「変更されました」）
- 通知の設定をしていない選手には端末に届かないが、通知済みとして扱う（アプリを開けばメニューは見える）。その旨をコーチに表示する

### 通知の許可

- 初回ログイン後、ホーム画面に「通知を受け取る準備をしましょう」の案内を出す（この端末で設定済みなら出さない。「あとで」で閉じられる）
  - iPhone で Safari のまま開いている場合は、ホーム画面への追加の手順を案内する
- 右上の「設定」画面（コーチ・選手共通）で、通知を有効にする／テスト通知を送る（Edge Function `push-self-test`）／この端末の通知をやめる

### 秘密情報

VAPID 秘密鍵と `CRON_SECRET` は Edge Function の Secrets に置き、`CRON_SECRET` は Cloudflare Worker の Secrets にも同じ値を置く。DB には秘密の鍵を置かない。

## 5. 行単位アクセス制御（RLS）

- すべてのテーブルで RLS を有効にし、許可していない操作はすべて拒否されるようにする
- 判定用の関数 `is_coach()` と `is_active_user()` を作る（security definer 指定。停止中なら false）

| テーブル | 選手 | コーチ |
| --- | --- | --- |
| profiles | 自分の行を読む | 全員分を読む（更新は Edge Function 経由） |
| events | 自分の分を読む・追加・更新。削除はメニューがない枠だけ | 全員分を読む。`change_ack_at` だけ専用の関数で更新 |
| event_cancel_history | 自分の分を読む | 読む |
| menus | 自分の枠のものを読む | すべての操作が可能（ドライランド枠かつ記録開始前に限る） |
| records | 自分の枠のものを読む・書く（メニューがある枠に限る） | 読む |
| templates / reference_notes / exercise_names | アクセス不可 | すべての操作が可能 |
| push_subscriptions | 自分の分のみ | 自分の分のみ |
| notifications | アクセス不可 | アクセス不可（Edge Function のみ） |

RLS だけでは表せない規則は、トリガーで強制する。

- メニューがある枠は削除できない（中止のみ）
- メニューがある枠は `kind` を変更できない
- 選手は `athlete_id`、`change_ack_at`、`changed_from` を直接変更できない
- 記録開始後は menus を更新・削除できない（Q1）
- メニュー設定済みの枠の日時・場所・時間が変わったら `changed_from` を記録し（最初の1回だけ）、`change_ack_at` をクリアする

### 参考メニュー帳とテンプレート（フェーズ5で実装）

- `reference_notes` と `templates` はコーチ専用。選手向けのポリシーはなく、選手からは1件も見えず、書き込みもできない
- 参考メニュー：タイトル（1〜100文字）、出典URL（空か http(s) のみ）、メモ（2000文字まで）、タグ（1〜20文字を10個まで）。元ページの文章や画像は保存しない
- タグの入力は「、」・カンマ・空白で区切る。よく使うタグ（体幹、肩、下半身、試合前、オフ期）と、これまでに使ったタグはボタンで選べる。一覧は選んだタグをすべて含むものに絞り込む
- テンプレート：メニューと同じブロック形式（`validate_menu_blocks` で検証）。参考メニューの詳細から「このメモからテンプレートを作る」で作ると、タイトルとメモを引き継ぎ、元の参考メニューと紐づく。参考メニューを削除してもテンプレートは残る
- テンプレートで使った種目名も、種目名の候補に入る
- メニュー作成画面の「テンプレートから入れる」：空なら入れる、メニューがあれば「置き換える」か「末尾に追加」を選ぶ。入れるときにブロックと種目の ID を付け直す（同じテンプレートを2回入れても重複しない）。保存はコーチが「メニューを保存」を押したとき
- メニュー作成画面の「このメニューをテンプレートに保存」で、今のメニューをテンプレートにできる
- コーチの下部メニュー：カレンダー／テンプレート／参考メニュー／選手管理

### 画面の更新（フェーズ7で調整）

- コーチと選手が同じデータを見るため、画面を開くたびに最新を読み直す（TanStack Query の `staleTime: 0`）
- 左上の「SWIM D-work」はカレンダーへのリンク。設定画面には「← カレンダー」を置く

### アカウント

- Supabase Auth の新規登録は無効にする
- **ログインはメールで届く6桁のコードをアプリに入力する方式**（要件書の「メールのリンクでログイン」から変更）
  - iPhone ではメールのリンクが Safari で開き、ホーム画面のアプリにはログイン状態が渡らないため
  - `signInWithOtp({ shouldCreateUser: false })` でコードを送り、`verifyOtp({ type: 'email' })` で確認する
  - メール文面は Auth の Magic Link テンプレート（`supabase/templates/magic_link.html`）。コードと「はじめて使う方へ」の手順を載せる
- **profiles はトリガー `handle_new_user` が作る**。コーチがまだいなければ最初のユーザーがコーチ、以降は選手。選手の色は空いている色から自動で割り当てる
- 招待は Edge Function `invite-athlete`
  - 呼び出した人が有効なコーチかを確認する
  - 同じメールアドレスが登録済みなら断る。選手は5人まで（停止中は数えない）
  - `auth.admin.createUser({ email_confirm: true })` でユーザーを作り、そのアドレスにログインコードのメールを送る
  - Supabase の招待メール（`inviteUserByEmail`）は使わない。リンクを押すまでメール未確認のままになり、コードでログインできないため
- 停止・再開は Edge Function `set-athlete-status`。`profiles.is_active` とアカウント凍結（ban）の両方を切り替える
- 削除は Edge Function `delete-athlete`。**停止中の選手だけ**を削除できる（停止 → 削除の2段階）。画面では選手の名前を入力して確認する。Auth のユーザーを削除すると、外部キーの連鎖でプロフィール・予定・メニュー・実施記録・中止履歴・購読・通知がまとめて消える（取り消せない）。テンプレート・参考メニュー帳・種目名の候補は残る
- コーチの選手一覧は関数 `list_athletes()`（コーチのみ。最終ログイン日時から「招待中／利用中」を表示する）
- 最初のコーチアカウントは、Supabase 管理画面の「Create new user（Auto Confirm User）」で作る（`docs/setup.md`）

### 予定（フェーズ2で実装）

- 予定を追加・変更・中止・削除できるのは、有効な選手本人だけ（RLS）。コーチは全員分を読むだけ
- 選手は `athlete_id`（持ち主）を変えられない。`changed_from` と `change_ack_at` は、利用者が更新しても元の値に戻る（トリガー）
- 中止には理由（1〜100文字）が必須。中止・取り消しは `event_cancel_history` に残る。通常に戻すと予定の中止理由は消えるが、履歴には残る
- コピーされるのは枠（種類・開始時刻・場所・時間）だけ。貼り付けは選んだ日ごとに1件追加し、既存の予定は上書きしない
- 「メニューが入った枠は削除できない」「メニュー設定後の変更を記録する」は、フェーズ3でトリガーを追加した（下記）

### メニュー（フェーズ3で実装）

- メニューを入れられるのは、中止されていないドライランド枠だけ（RLS とトリガー）。書き込めるのはコーチだけ
- 形式の検証は DB の `validate_menu_blocks()`（CHECK 制約）と `src/lib/menu.ts` の zod スキーマの両方で行う。ブロックは1〜30個、サーキットの種目は1〜15個、回数・秒数は1〜9999の整数、ブロックと種目の ID は重複不可
- 種目名の候補 `exercise_names` は、メニュー保存時のトリガーが自動で追加・更新する（コーチだけが読める）
- メニューが入った枠を選手が削除しようとすると拒否される。種類も変更できない（アカウント削除に伴う削除は通す）
- メニューが入った枠の日時・場所・時間が変わると、`changed_from` に**変更前の値**を残す（2回目以降の変更では最初の値のまま。元の値に戻すと消える）
- コーチが「確認済みにする」を押すと（関数 `acknowledge_event_change`）、`changed_from` を消して `change_ack_at` を記録する。その後にまた変更されれば、確認時点の値から改めて記録する
- 一括貼り付け：今日から4週間の、有効な選手のドライランド枠から選ぶ。メニューがある枠は「設定済み・上書き」と表示し、選んだときだけ上書きする。貼り付けと同時に、編集中の元の枠も同じ内容で保存する
- コーチのカレンダーは週表示（今日から7日）。選手で絞り込める。停止中の選手は初期状態で非表示
- 選手への通知ボタン（「保存して選手に通知」）と「未通知」の印はフェーズ6で追加する

### 実施記録（フェーズ4で実装）

- `records` は1枠に1行。書けるのは有効な選手本人だけで、メニューが入った、中止されていない自分の枠に限る。コーチは読むだけ。削除は誰もできない
- 形式（DB の `validate_record()` で検証）
  - `exercise_results`：`{ 種目ID: { checked, value, load } }`。`value` と `load` は**計画と違うときだけ**値を入れ、同じなら `null`
  - `block_results`：`{ ブロックID: { sets | rounds } }`。単独は実施セット数、サーキットは実施周回数。計画と同じなら `null`
  - `added_exercises`：選手が追加した種目（メニューの種目と同じ形式、20個まで）
- 完了は `records.completed_at`（`events.completed_at` は使わないため削除した）
- `started`（記録開始）はトリガーが計算する。条件は1章「Q1 の記録開始の定義」のとおり
- 記録開始後は、コーチはメニューを変更・削除できない（トリガー）。コーチの画面は確認画面に切り替わり、一括貼り付けの候補からも外れる
- 選手の記録画面は入力のたびに自動保存（約0.8秒後、画面を離れるときにも保存）。名前が空の追加分は、名前を入れるまで保存しない
- カレンダーの印：メニュー未設定／メニューあり／実施中（記録開始・未完了）／実施済み（完了）
- コーチの確認画面：計画どおりは通常表示、数値を変えた種目とセット数・周回数は「計画 → 実績」、未チェックは赤、追加分は青で表示し、件数を上部にまとめる

## 6. 表示上の決まり

- 秒の値は、60で割り切れれば「5分」、割り切れなければ「1分30秒」のように表示する（入力と保存は秒）
- 予定の種類の色：選手画面は種類別、コーチ画面は選手別
- 月表示は日曜始まりのマス目で、その月の1日から月末までを表示する（前後の月の日は薄く表示）
- 週表示は今日を先頭に7日間。左右スワイプか「前の7日／次の7日」で7日ずつ移動する
- 枠の印：未設定／設定済み／未通知（コーチのみ）／実施中／実施済み／変更あり（コーチのみ）／中止
